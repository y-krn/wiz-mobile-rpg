# Issue #440: magic coreChance sweep

Closes #440

## 結論

採用設定は次のとおり。

- `AFFIX_BALANCE.rollComposition.magic = { support: 1, core: 1, coreChance: 1.00 }`
- `AFFIX_BALANCE.budgetsByRarityAndFloor.magic = [0, 10, 10, 10, 10, 10]`
- 装備選択の `SIM_CORE_SCORE_DROP_TOLERANCE=0.10`

主状態 `workshop-core-pools` のB20で、終了時にcoreを1個以上装備している割合は
`37.2% [33.1%, 41.5%; N=500]`。目標帯35〜40%の点推定に入る。2個以上は
`18.2% [15.1%, 21.8%; N=500]`。

今回の掃引で点推定が目標帯に入ったのはこの設定だけだった。`coreChance=0.50`
以下の最大値は許容幅0.10でも29.0%、許容幅0の`coreChance=1.00`は32.4%で、
無理に目標帯へ寄せる設定は採用していない。CIは目標帯の端をまたぐが、N=500の
Wilson CIであり「未確定」ではない。目標判定はIssueで指定された点推定に基づく。

## 予算を変えない条件

coreのflat costは10、採用前の現行magic予算はB1以外3なので、core poolに入るcoreがない。
この場合は`rollAffixLoadout`がcoreChanceを引く前にsupportへフォールバックするため、
coreの生成は「未観測」ではなく現行予算では到達不能。

採用前のorigin/main baselineで、magic予算を`[0,3,3,3,3,3]`のままにした4点
(0.00/0.10/0.25/0.50)は、score低下許容
0では現行t0と同じ出力、0.10では現行t0.10と同じ出力になった。B20の主値はそれぞれ
13.8% / 16.4%の装備率で、予算を10へ変えた条件とは分けて扱った。

## 採用設定の副作用と交換レート

現行設定と同じscore低下許容0.10で比較すると、現行→採用設定は次の差だった。

- 装備率: 16.4% → 37.2%（+20.8pt）
- 平均到達階: 2.06 → 2.28（+0.22階）
- 素材EV/時間: 0.0735 → 0.0784（+0.0049）
- bank素材EV: 10.47 → 13.73（+3.26）
- core定着率: 72.6% → 84.9%
- B5: entrant 8.0% → 10.8%、突破 45.0% → 42.6%、死亡 47.5% → 53.7%
- B10: entrant 2.4% → 1.8%。突破/死亡はN=12/9で未確定。
- 鑑定粉/run: 入手4.43 → 4.81、消費3.57 → 4.01、終了残量0.85 → 0.80、
  枯渇率49.0% [44.6, 53.4] → 49.4% [45.0, 53.8]
- 工房買い切り（run開始）: 19.2% [16.0, 22.9] → 20.6% [17.3, 24.4]

同じscore方針での交換レートは、装備率+1ptあたり平均到達階+0.0106、
素材EV/時間+0.000235、bank素材EV+0.157。したがってこの測定では「深度とEVを払う」
代償ではなく改善側だった。ただし生成構成変更で乱数消費順も変わるため、これは同一seedの
記述比較であり、pairedな因果効果とは呼ばない。

実際の現行方針（score低下許容0）から採用設定への総差は、装備率+23.4pt、平均到達階
+0.20、素材EV/時間+0.0040、bank素材EV+2.20（+1ptあたりそれぞれ+0.0085階、
+0.000171、+0.094）。現行設定だけで許容幅を0→0.10へ変えた測定は装備率+2.6pt、
平均到達階-0.02、素材EV/時間-0.0009、bank素材EV-1.06であり、選択方針単独の効果と
magic生成変更の効果を混同しない。

## 乱数消費順と測定側の切り分け

`coreChance`を持つmagic構成では、core poolが空でない場合に確率判定の乱数を1回消費する。
そのため予算あり`coreChance=0`はcoreを生成しなくても現行と出力が一致せず、同一seedでも
estimandが変わる。予算なし条件だけ現行と同じになったのは、core pool空判定で確率抽選へ
進まないためであり、測定バグではなくgeneratorの分岐で説明できる。

保存済み乱数列による反実仮想は今回実装していない。したがって掃引値は同一seedでの
記述的比較として報告する。`origin/main`のfull-depth runnerでB5/B10/B15/B20を同一task内で
実行し、各top-level resultのsnapshotを使った。旧固定B20-only runnerの値は、先行深度の
乱数消費を含まない別estimandなので最終判定から除外した。
